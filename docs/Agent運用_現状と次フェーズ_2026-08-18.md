# Agent運用：現状と次フェーズ

- 監査日: 2026-08-18
- 対象: `higgs1729/react-shadcn` の GitHub 最新 `main`
- 対象コミット: `57e9aa295565e0a5abd1e93ad10672107cbdd849`
- 確認方法: `git fetch origin main --prune` 後、local `HEAD` と `origin/main` が同一であることを確認
- 変更方針: 本監査では設定・ソースを変更せず、調査報告だけを作成

## 0. 結論

この repo は単なる Next.js monorepo ではなく、すでに次の3層を持つ。

1. **Agentへの入力層**: `AGENTS.md`、`CLAUDE.md` shim、プロジェクト Skill
2. **Agentの実行層**: MCP、Stop hook、Claude/Codex の permission 設定
3. **Agentの成果物検証層**: `validate`、`checks`、契約 validator、pipeline validator、決定論的 eval、Storybook/Vitest/Playwright

品質の中心はかなり良い。特に、AGENTS/CLAUDE の同期検査、契約付き handoff、決定論的 eval、テストの自動発見は、自分専用の基盤に残す価値が高い。

一方、現在の主な負債は機能不足ではなく **配布先の複製と実行経路の分断** である。

- shadcn Skill が `.agents` / `.claude` / `.hermes` に3重配置されている
- dispatch Skill は `.agents` / `.claude` に複製され、`.hermes` にはない
- Skill 全体の同期検査はない。現在検査されるのは `AGENTS.md` と `CLAUDE.md` の組だけ
- `validate:pipeline`、`validate:provenance`、`scan:secrets` など強い検査が個別コマンドのまま
- CI で Chromium をインストールしているのに、`test:smoke` は `run-tests.mjs` の除外対象のまま
- repoには permission/sandbox の正本がなく、ローカルの ignored な `.claude/settings.local.json` に古い・広い許可が残る

したがって次フェーズは「新しい Agent 製品を追加する」ではなく、**一つの canonical policy と、一つの検証ゲートから各 Agent へ配信する基盤へ整理する**のがよい。

## 2. 良い部分：自分専用基盤に残す

### A. `AGENTS.md` を正本、`CLAUDE.md` を固定 shim にする構造

`apps/studio/scripts/check-agent-instructions.mjs` が、Git管理対象全体を `git ls-files` で列挙し、すべての `AGENTS.md` に同一内容の `CLAUDE.md` shim があることを検査している。

これは以下を同時に満たしている。

- Agentごとに指示を二重管理しない
- Windowsで symlink/junction を repo に持ち込まない
- ルールの所在を `AGENTS.md` に固定する
- 子ディレクトリの規則を近くに置く

実測でも `13 AGENTS.md/CLAUDE.md node(s)` の同期検査は成功した。これは残す。

### B. Stop hook の「登録」と「本体」の分離

`.codex/hooks.json` と `.claude/settings.json` は登録だけを持ち、実処理は `scripts/stop-validate.mjs` に一元化している。Node ESMで実装しているため Windows の shell 差異を抑え、`stop_hook_active` による再入防止もある。

repo固有の `npm run validate` を公式 lifecycle hook に接続するための自作として妥当。hook本体は残す。ただし後述の通り、毎ターン実行の重さは次フェーズで調整する。

### C. handoff と検証を JSON Schema / Ajv で固定していること

`apps/studio` の FlowSpec / SelectionSpec / BuildReport と、`validate-pipeline.mjs` の cross-artifact 検証は、LLMの自己申告に依存しない。

`apps/studio/eval/` も、LLMを grader にせず、golden datasetを決定論的に評価している。`--candidates` で将来の live agent output を外から投入できる設計も有力。

### D. test/CIの自動発見

`run-tests.mjs` は package.json の `test:*` を列挙し、新しいテストの追加忘れを防ぐ。`run-checks.mjs` は contracts、lint、typecheck、tests、build、storybook を BuildReport 形に集約する。

今回の実測では次が成功した。

- `npm -w apps/studio run test:all`: 24/24 pass
- `npm -w apps/studio run validate:pipeline`: 2 flow pass
- `npm -w apps/studio run validate:provenance`: 2 manifest pass
- `npm -w apps/studio run scan:secrets`: 390 tracked files、0 findings
- `npm -w apps/studio run validate:agents`: pass
- `npm -w apps/studio run validate:docs`: pass
- `npm -w apps/studio run test:eval`: positive dataset pass、failing fixture検出 pass
- `npm -w apps/studio run validate:schemas`: 5 schema pass
- `npm -w apps/team-t run validate`: 177 pages / 200 APIs の検証 pass

## 3. 重複：減らすべきもの

### A. shadcn Skill の3重コピー

SHA-256比較で、次の **48 files** は同一内容の配布コピーだった。

- `.agents/skills/shadcn/`
- `.claude/skills/shadcn/`
- `.hermes/skills/shadcn/`

`SKILL.md` だけでなく、CLI、registry、MCP説明、rules、eval、画像、`agents/openai.yaml` まで全体が複製されている。

これは今は一致しているが、更新時にどれか一つだけ変わる。次フェーズでは、以下のどちらかにする。

- Gitで保持する canonical copy を一つにし、各クライアントへの配信を生成・検証する
- どうしても通常ファイルを3か所に置くなら、全ディレクトリの hash 同期検査を追加する

この repo の Windows / `core.symlinks=false` 前提では、repoに junction を保存するより「canonical + sync script」の方が再現性が高い。

### B. dispatch Skill の2重コピー

`.agents/skills/dispatch/SKILL.md` と `.claude/skills/dispatch/SKILL.md` は同一。`.claude` 側にはさらに `evals/evals.json` があるが、`.agents` 側と対応していない。

dispatch は内容に Claude 固有の `Explore`、`SendMessage`、`Workflow`、`haiku` が多く、Codex/Hermesをまたぐ project skill としては適用範囲が曖昧。全面複製を続けるより、ユーザー層の運用ポリシーと project固有の作業手順を分離する。

### C. `.mcp.json` と `.codex/config.toml`

これはJSON/TOMLで形式が違うので完全重複ではないが、同じ shadcn MCP の command/args を2か所で持つ。クライアントごとの公式配置先が異なるため二つ必要。ただし、対象 cwd やサーバー名がずれた場合に検出できる同期チェックがない。

## 4. 公式機能へ委ねられる部分

ここでいう「置換」は外部製品を増やす意味ではなく、Agentクライアントが公式に提供する配置・実行機構を使い、自作コードを減らす意味である。

| 現在の自作・運用 | 公式機能へ委ねる範囲 | 自作で残す範囲 |
|---|---|---|
| `CLAUDE.md` の内容を独自に二重記述 | Claude/Codex/Hermesの instruction loader に読ませる | `AGENTS.md` のrepo固有事実、shim検査 |
| Skill配布 | 各クライアントの公式 Skill discovery | canonical管理、revision固定、hash検査 |
| MCP起動 | `.mcp.json` / `.codex/config.toml` の公式MCP登録 | shadcn MCP自体ではなく、対象workspaceの設定検査 |
| Stop hook登録 | Claude/Codexの公式 lifecycle hook | `npm run validate` と短いエラー要約 |
| permission/sandbox | 各クライアントの公式設定 | repo規約に「権限を要求する」と書くのではなく、設定を別管理 |
| UI生成 | shadcn CLI/MCP | `packages/shadcn-kit`、Base UI、編集禁止境界の検査 |
| eval実行 | 公式のAgent runnerが candidate を生成 | `apps/studio/eval` の決定論的 grader、golden data |

特に、一般論の「良い考え方」をSkillに詰め込むより、公式 loader、hook、MCP、permission の設定と、repo固有の検証を組み合わせる方が保守しやすい。

## 5. 自作を残すべき部分

以下は shadcn、Claude、Codex、Hermes の公式機能だけでは代替できない repo固有の資産である。

1. ルートと各workspaceの `AGENTS.md`
2. `CLAUDE.md` の固定 shim と `check-agent-instructions.mjs`
3. `scripts/stop-validate.mjs`
4. `apps/studio` の FlowSpec / SelectionSpec / BuildReport 契約
5. `validate-pipeline.mjs` と `validate-provenance.mjs`
6. `apps/studio/eval/` のケース、grader、fixture
7. `run-tests.mjs` の自動発見と `run-checks.mjs` の BuildReport化
8. `scan-secrets.mjs` の credential-free scan
9. `packages/shadcn-kit` の編集禁止境界、Base UI規約、registryとの整合性
10. GitHub Pages の複数workspace合成・deploy手順

これらは「AIにどう考えさせるか」ではなく、「AIが何を出しても何を通すか」を定義している。自分専用の開発基盤の中核にする。

## 6. 未使用または接続が弱い有力機能

優先度の高い順に記す。

### P1: `test:smoke` がCIゲートから外れている

`run-tests.mjs` は `test:smoke` を「Chromium downloadが必要」として除外する。一方 `.github/workflows/checks.yml` は先に `npx playwright install --with-deps chromium` を実行している。

つまり、CIはブラウザを準備しているのに、studioの smoke test は `test:all` から実行されない。除外理由が現状とずれている可能性が高い。

### P1: live agent eval の接続口が未接続

`run-eval.mjs --candidates <dir>` は live model output を受け取れるが、Agentを呼び出すrunnerはrepo内にない。golden datasetは実働だが、現在は埋め込みcandidateとfixtureの回帰検査が中心。

次フェーズでは、Agent呼び出し自体をCIに入れるのではなく、手元専用の `eval:candidate` ラッパーを作り、生成物を一時ディレクトリに出して同じgraderへ渡せるようにするのが安全。

### P1: pipeline/provenance/secret scan の入口が分散

実装はあり、単独実行も成功する。しかしstudioの `validate` と `run-checks` の固定6項目には、これらの実データ検査が直接入っていない。関連する `test:*` は `test:all` で動くが、「現行成果物を直接検査するゲート」と「validator自身の回帰テスト」が混ざっている。

検証の意味を明確にするため、次のどちらかに整理する。

- `validate` に deterministic な artifact checks を含める
- `validate` は schema/契約だけに限定し、`checks` の正式な名前付き項目に `pipeline`、`provenance`、`secrets` を追加する

### P2: Skill eval metadata が実行経路を持たない

`.agents/skills/shadcn/evals/evals.json` と `.claude/skills/shadcn/evals/evals.json` などは、Skillの期待動作を記録しているが、repoの `npm run checks` からは実行されない。これは削除対象というより、`apps/studio/eval` との責務を明示的に分けるか、Skill smoke harnessへ接続する候補。

`agents/openai.yaml` もUI表示用のmetadataに見え、repo内の実行参照は確認できなかった。Skill配布に必要なクライアントだけに残す。

### P2: `dispatch` の適用範囲が実行環境と不一致

`/dispatch` という明示呼出しに限定している点は暴発防止として良いが、内容は特定Agentのsubagent語彙に依存する。HermesプロジェクトSkillには同じdispatchがなく、クライアント横断の正本になっていない。

## 7. 壊れやすい部分

### A. ignored な `.claude/settings.local.json`

GitHub対象には含まれないが、現在の実機には存在する。内容には以下がある。

- `Bash(git add *)`
- `Bash(git init *)`
- 特定コミットを許可するルール
- `C:\Users\tomoy\Desktop\react-shadcn` という旧パス
- PowerShellコマンドの長い完全一致 allowlist

これは「広い権限」そのものより、古いパスと完全一致文字列に依存する点が壊れやすい。自分専用の全権運用を維持する場合でも、現行 `C:\dev\react-shadcn` に合わせ、許可・確認・記録の方針を一つのローカル正本にするべき。repoへ取り込むべきではない。

### B. MCPの絶対パス

`.mcp.json` と `.codex/config.toml` の `C:\dev\react-shadcn\packages\shadcn-kit` は、このPCでは正しいが clone先では壊れる。個人PC固定なら許容できるが、基盤化するならセットアップスクリプトで現在のworkspace rootから生成する。

### C. Stop hookの常時実行

毎回 `npm run validate` を起動するため、Agentの終了操作がworkspace全体の状態に拘束される。`stop_hook_active` による再入防止はあるが、validateが遅い・一時的に壊れる・別workspaceの変更で止まるという結合が強い。

次フェーズでは、通常の短い `validate:fast` と、完了時の全量 `validate` を分離する。ただし「検証を削る」のではなく、hookの終端ゲートを速い決定論的チェックにする。

### D. 文書と実装の古さ

`docs/MULTI_AGENT_SETUP.md` は「このrepoにはプロジェクト固有MCPを設定していない」と記録しているが、現物には `.mcp.json` と `.codex/config.toml` がある。今回の監査結果では、現物を正として、この文書は更新候補と判定する。

## 8. 次フェーズ：自分専用 Agent開発基盤の目標形

### canonical

```text
repo/
  AGENTS.md                         # repo固有の事実・境界
  CLAUDE.md                         # 固定shim
  .agents/skills/                   # project skillのcanonical
  .claude/skills/                   # 配布先（生成または同期検査）
  .hermes/skills/                   # Hermes配布先（必要なものだけ）
  .mcp.json                         # Claude系の公式登録
  .codex/config.toml                # Codex固有形式の登録
  .codex/hooks.json                 # Codex固有hook登録
  .claude/settings.json             # Claude固有hook登録
  scripts/                          # repo固有の実行本体
  apps/studio/eval/                 # deterministic eval
```

### 実行の一方向化

```text
AGENTS.md / canonical Skill
          ↓
client loader (Claude / Codex / Hermes)
          ↓
MCP・hook・Agent execution
          ↓
validate:fast → validate → checks → build/deploy
          ↓
report / provenance / eval artifact
```

### 実施順

1. **P1**: `test:smoke` の除外理由とCI実態を一致させる
2. **P1**: Skill全体hashの同期検査を追加する。`AGENTS`/`CLAUDE`検査とは別にする
3. **P1**: `validate`、`checks`、`test:*`、`eval`、live candidate の責務を README 1枚に固定する
4. **P1**: `docs/MULTI_AGENT_SETUP.md` のMCP記述を現物へ合わせる
5. **P2**: pipeline/provenance/secrets を名前付きcheckとしてゲートへ接続するか判断する
6. **P2**: dispatch eval と shadcn eval の実行主体を決め、使わないmetadataを配布しない
7. **P2**: ignored local permission の旧パス・完全一致allowlistを整理する
8. **最後**: 必要性が実証された場合だけ新しいSkill/MCP/cronを追加する

## 9. 監査時点の判断

- **良い部分**: 契約検証、deterministic eval、自動テスト発見、AGENTS/CLAUDE同期、repo固有hook
- **重複**: Skillの3重コピー、dispatchの2重コピー、MCP設定の手動二重管理
- **公式機能で置換可能**: Skill/MCP/hook/permission の登録とloader部分。repo固有ポリシーとgraderは置換しない
- **自作を残すべき**: AGENTS、契約、pipeline/provenance、eval、checks、secret scan、shadcn-kit境界
- **未使用の有力機能**: smoke test、live candidate eval、pipeline/provenance/secretsの正式ゲート、Skill eval metadata
- **壊れやすい部分**: ignored permission設定、絶対パス、Stop hookの全量結合、Skill同期不在、MCP記録の文書ドリフト

この repo は、Agent機能を増やす段階ではなく、すでにある検証資産を「一つの canonical policyから配信し、正式なゲートを一つの実行グラフにする」段階にある。
